# Changelog

Changes that matter to someone running cyberspace-mcp. Newest first.

## Unreleased

- **Builds, a trash, and deletes that keep what they should.** After "delete the obstacle run" took a 31-piece castle that shared a bag with the course, with no backup and no warning:
  - **Builds.** `place`, `hide`, `forge_item`, `seal_chest` and `seal_door` take `build`, a label such as "obstacle run"; with none, the piece goes to the current build (`build_use`), else to "unlabelled". New tools: `builds`, `build` (one build's pieces, checked against what is placed: there, moved, missing), `build_add` (record things already placed under a build, by id, name match or whole bag; a thing of another build only with `move: true`: how pieces placed before this release get their builds), `build_rename`, `build_use`, `build_notes`. The ledger follows a piece through `move_placed`, `constrain_placed` and deletes. Labels live only in `builds.json` on this machine; nothing published names them.
  - **Notes.** `notes` reads, appends to or replaces `notes.md`, the agent's own notes on what it built where, and why (64 KB at most).
  - **A backup before every delete.** `remove_placed` and the new `delete_build` first write `trash/<time>-<label>/` in the state directory: the signed bags as they were, removed sealed objects, the removed pieces opened (a shard's whole payload, a message's text), their ledger entries and what stayed. Never a region key, an item's secret or a Cashu token. No backup, no delete. `trash` lists the entries; `restore_build` puts the original entries back into their bags exactly (the same ids, keys, chests, doors and coins included), deriving the region key again from the place; a shard sealed by reference whose object was taken down comes back sealed again under a new address; a piece from a locked room only into that room, while its door is held. A restore cut short is tried again for the rest only.
  - **Scoped deletes.** `delete_build` takes one build (or pieces by id) out of every bag it is in and keeps everything else; only a bag left empty is deleted. `remove_placed` of a whole bag that holds more than one build is now refused, pointing at `delete_build`; so is one holding things in no build unless the operator approves deletes (name them with `build_add` first), and `delete_build` of "unlabelled".
  - **A preview, and the operator's approval.** `delete_build` without `confirm` changes nothing and shows what would go and what would stay in each bag. A delete of more than 5 pieces (`deleteApprovalThreshold`), or a whole-bag `remove_placed` of things in no build, waits for the operator's code by DM, as a payment does under `paymentApproval` (`DEL-...` codes, 30 minutes, used once, bound to exactly the pieces previewed). Deletes made in the last hour without approval count toward the threshold, so a large delete cannot be split into small ones. `deleteApproval` (`--delete-approval`, config.json) is `"operator"` by default when an operator is configured, else `"none"`; `doctor` reports it.
- **Your agent's profile follows its relays.** When none of the relays that accepted the agent's last profile are configured any more, `identity` publishes it again on the current relays instead of answering "unchanged". `serve` does the same once at startup, with no call needed: it publishes the same content and tags, signed again. An agent set up on the old default relays (`wss://cyberspace.nostr1.com`, `wss://onosendai.feeds.relay.tools`, the defaults before #95) moves its profile to `wss://relay.onosendai.tech` on its own, so ONOSENDAI's AGENTS panel finds it there.
  - **When the outbox still holds the profile event,** its replay at startup already sends that same event, unchanged, to the current relays. Nothing is signed again, and `profile.json` (and so `doctor`) lists the new relay.
  - **A refusal is not retried at startup.** If every current relay refused the profile, `profile.json` notes the refusal and keeps listing the relays that still hold it, so `doctor` and `visit` keep working. When the current relays could not be reached, the next start tries again. A profile no relay ever accepted is left alone.
  - **An `identity` call made while the startup republish runs** waits for it, so an edit made in that call is never undone.
  - **A profile that names an operator other than the configured one** is never republished.
